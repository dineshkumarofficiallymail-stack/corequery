CoreQuery Architecture & Defence-in-Depth

Applying LLMs safely to core banking operations: how CoreQuery prevents hallucinations, blocks unauthorized actions, and self-corrects.

1. Schema Linking & Domain Glossary

Instead of overloading the prompt with an entire core banking dictionary, keyword-based schema linking identifies relevant tables and includes foreign key parents. Injects exact categorical enum values (e.g., 'SAVINGS', 'RETURNED').

2. Static AST / Regex Guardrails

Every SQL statement passes static inspection. Validates that queries start with SELECT/WITH, enforces single-statement execution, blocks forbidden commands (DROP, DELETE, PRAGMA) and restricted SQLite internal functions.

3. Read-Only DB Connection

Even if static validation were bypassed, the SQLite connection is opened in strict read-only mode (mode=ro) with statement cancellation timers (5s timeout) and a hard 200-row cap.

4. Self-Repair Feedback Loop

When an error occurs (e.g. wrong column or typo), CoreQuery catches the SQLite exception, feeds it back to the model, and allows up to 2 repair iterations. Most SQL mistakes resolve on attempt #2.

5. Golden Set Evaluation

25 golden core-banking questions spanning easy, medium, and hard levels. Scored on execution accuracy (whether the executed result set matches the golden query output rather than surface text matching).

6. Provider Neutrality

Single lightweight HTTP contract matching the OpenAI Chat Completions standard. Groq, OpenAI, Together, or local Ollama are swappable via configuration.
